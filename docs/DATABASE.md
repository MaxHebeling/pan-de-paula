# Base de datos

Postgres 17 (local en desarrollo, Supabase en staging/producción). **Las migraciones SQL son la fuente de
verdad**: esquema, restricciones y la lógica crítica del negocio viven en la base y se prueban con tests de
integración (`packages/db/test`). Los tipos TypeScript se generan desde la base (`kysely-codegen`).

## Comandos

| Comando                                       | Qué hace                                                                                                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm db:migrate`                             | Aplica las migraciones pendientes de `packages/db/migrations` a `DATABASE_URL` (una transacción por archivo, advisory lock, checksum en `schema_migrations`)     |
| `pnpm --filter @pdp/db run migrate:status`    | Lista aplicadas (✔) y pendientes (·)                                                                                                                             |
| `pnpm db:codegen`                             | Regenera `packages/db/src/generated/db.ts` (ignorado en git; correr tras cada migración)                                                                         |
| `pnpm db:seed`                                | Seed idempotente: admin (`SEED_ADMIN_*`), negocio, categorías, 16 ingredientes, 16 productos, recetas, recompensas, cupón BIENVENIDA. Re-ejecutable, nunca borra |
| `pnpm db:reset -- [--test] [--seed]`          | **Solo localhost**: dropea y recrea la base, migra y opcionalmente siembra. Rechaza hosts remotos y `APP_ENV=production`                                         |
| `pnpm db:test` / `pnpm --filter @pdp/db test` | Tests de integración: `global-setup` recrea `DATABASE_URL_TEST` desde cero y migra                                                                               |
| `pnpm check:migrations`                       | Numeración creciente sin duplicados y checksums intactos de las publicadas (`RELEASED`)                                                                          |
| `bash scripts/release-migrations.sh`          | Marca las migraciones actuales como publicadas (agrega checksums a `RELEASED`)                                                                                   |
| `pnpm --filter @pdp/db run import -- …`       | Importador desde Google Sheets (ver `MIGRATION_SHEETS.md`)                                                                                                       |

## Política de migraciones

- Archivos `NNNN_nombre.sql` en `packages/db/migrations`, aplicados en orden. Se permiten huecos: cada módulo
  tiene un rango reservado (`0001–0009` núcleo · `0010–0019` catálogo/recetas · `0020–0029` POS/caja ·
  `0030–0039` producción/inventario/pedidos · `0040–0049` clientes/fidelización/reportes · `0050–0059` sitio
  público · `0060–0069` integraciones · `0070–0079` importación/observabilidad).
- **Inmutables una vez publicadas.** `migrate.ts` falla si el checksum de una migración aplicada cambia;
  `check-migrations.sh` (CI y deploy) falla si cambia una listada en `RELEASED`. Para corregir: nueva migración.
- **Aditivas y compatibles hacia atrás**: la versión anterior de la app debe seguir funcionando durante un
  rollback de aplicación (nunca `drop column` / renombrar en la misma migración que la app nueva empieza a usarlo;
  primero agregar, desplegar, después limpiar en una migración posterior).
- Tras migrar: `pnpm db:codegen`. Las tablas nuevas se agregan a `truncateAll` en `packages/db/test/helpers.ts`.
- Lógica crítica (dinero, inventario, puntos, pagos) va en funciones SQL transaccionales con el estilo de
  `0008_transactions.sql`; nunca se reimplementa en TypeScript.

## Invariantes (lo que los tests protegen)

- **Dinero en centavos enteros** (`integer`/`bigint`); costos unitarios de insumos en `numeric(18,8)`.
  `orders_total_chk`: `total = subtotal − descuento + envío + IVA + propina`.
- **Append-only**: `inventory_movements`, `ingredient_movements`, `loyalty_transactions` y `domain_events`
  rechazan `UPDATE/DELETE` por trigger. El nivel de stock siempre se puede reconstruir (`rebuild_inventory_levels()`).
- **Snapshots**: `order_items` guarda nombre, precio y costo al vender; `sales` no se edita (solo `voided_at`).
  Cambiar recetas o precios hoy no reescribe ventas de ayer.
- **Idempotencia**: `orders.idempotency_key`, `payments.idempotency_key`, `payments(provider, external_id)`,
  `webhook_events(provider, external_id)`, `sales.order_id` único, `orders.source_ref` único para importaciones.
- **Precios del servidor**: `create_order` ignora precios enviados por el cliente salvo `allow_price_override`.
- **Una sola fórmula de costeo**: `product_cost_cents`, `product_cost_impact`, `recipe_costing` y `recipe_formula_breakdown`
  pasan por `recipe_cost_terms`; `@pdp/domain` la espeja solo para previsualizar y `parity.test.ts` falla si divergen.
  Con `costing_settings` en sus defaults y sin overrides, el costo es idéntico al de `0003`.
- **Una caja abierta a la vez**; **un cliente por teléfono/email** (índices únicos parciales).
- **Seguridad**: RLS en todo; `anon`/`authenticated`/`PUBLIC` sin privilegios; la app entra como `pdp_app`.
  Ninguna función es `SECURITY DEFINER` salvo `audit_row_change`.

## Conexión

`createDb()` (`packages/db/src/index.ts`): pool `pg` con `max` 3 en Vercel / 10 local, `statement_timeout`
20 s, `int8` → number con guarda de rango, `numeric` como string (exactitud). `dbHealth()` cuenta
`schema_migrations` y alimenta `/api/ready`. En Supabase usa el **pooler en modo transaction** (puerto 6543):
no dependas de `SET`/`prepared statements` de sesión fuera de una transacción (por eso `set_config(..., true)` es local a la transacción).
